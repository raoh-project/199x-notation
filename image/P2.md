# P2

P2 is the second format a machine is written in as an image, and the one for a deterministic
machine. This file is its definition: what text is an image of P2, and what an image that is one
accepts. It is not taken from any implementation's code, and every implementation that reads or
writes P2 is held to it. How a pattern becomes a machine, which machine an implementation writes,
and how many characters it writes at most are not part of the format; the [README](../README.md)
says what a writer promises.

A P1 image says whether its machine is deterministic, and a reader has to find out whether that is
so. A set is written once however many states step over it, so finding it out goes over the same
sets again at every state that steps over them, which the image's length does not bound. P2 does not
say it. It cuts the scalar values into classes, each scalar value in exactly one, and gives every
state exactly one state to go to for every class. So every image of P2 is deterministic, and no text
can say otherwise.

## What an image is written in

An image is text in ASCII. It begins with the marker `P2`, and after the marker comes a sequence of
numbers, each one after a comma:

```
image  = "P2" 1*( "," number )
number = "0" / ( %x31-39 *%x30-39 )
```

So a number is 0 or decimal digits that do not begin with 0. Nothing else is written: no sign, no
space, no line break before, inside or after the image, no empty number between two commas, and no
comma at the end.

Every number is an integer from 0 to 2,147,483,647, and a text with a larger one is not an image of
P2, wherever the number stands and however many digits it has. A place may allow less, as the
sections below say. A later format that needs larger numbers is another format.

## The numbers in order

The numbers are, in this order:

1. Each piece, as its last scalar value and the class it is in.
2. The number of states, and then each state: 1 where a walk that ends there accepts and 0 where it
   does not, and then each of its spans as its last class and the state it leads to.

The pieces cut the scalar values, from U+0000 to U+10FFFF, into runs that follow one another. The
first piece begins at U+0000, each later one at the first scalar value after the last of the one
before it, and the last one ends at U+10FFFF, which is how a reader knows it is the last. The
surrogates, U+D800 to U+DFFF, are no scalar values, so a piece that ends at U+D7FF is followed by one
that begins at U+E000, and a piece may hold scalar values on both sides of them.

Classes are numbered from 0 in the order their first piece comes in. So the first piece is in class
0, and each later piece is in a class an earlier piece is in, or in the class one greater than the
greatest of those. A class may be in many pieces, as `[a-zA-Z]` is two runs and one class.

The spans of a state cut the classes in the same way: the first span begins at class 0, each later
one at the class after the last of the one before it, and the last one ends at the greatest class,
which is how a reader knows the state's spans are over. So a state leads to exactly one state on
each class.

The pieces and the spans are not counted, since where each ends is written in them. The states are
counted, because a span names a state that may come after it, and a reader holds the name to the
count as it reads it. States are numbered from 0 in the order they are written, and a span names
them by those numbers. The image ends with the last span of the last state.

`a+`, for example, is three pieces in two classes, and three states, of which only the second
accepts:

```
P2,96,0,97,1,1114111,0,3,0,0,2,1,1,1,0,2,1,1,0,1,2
```

Class 0 is every scalar value but `a`, and class 1 is `a`. State 0 leads to state 2 on class 0 and
to state 1 on class 1, and state 1 does the same. State 2 accepts nothing and leads to itself on
both classes, which is the one span ending at class 1.

## What makes an image one

An image is one where all of these hold:

- The last scalar value of each piece is a scalar value, no surrogate, and greater than the last of
  the one before it, and the pieces go on until one whose last is 1114111 (U+10FFFF).
- The first piece is in class 0, and each later piece is in a class at most one greater than the
  greatest class before it.
- Two pieces next to each other are in different classes.
- There is at least one state, the image holds as many as the count of them says, and whether each
  accepts is 0 or 1.
- The last class of each span of a state is greater than the last of the one before it, and the
  spans go on until one whose last is the greatest class.
- A span names a state the image has: one less than the count of states, or less.
- Two spans of one state next to each other lead to different states.
- Nothing follows the last state.

Nothing else is asked. A state no walk reaches may be written, and two states may lead to the same
states on every class.

Each of these is a look at the number being read and at what was read just before it, and the
greatest class and the number of states are known before any span is read. So whether a text is an
image of P2 is found out in one pass over it, with work linear in its length. How a matcher holds
the machine once it is read, as the spans or as a table it builds from them, is the matcher's and
not this.

A reader refuses text that is not an image of P2 before it matches anything, and refuses it as not
an image rather than failing in some other way. So a machine that was read answers every text it is
asked about.

## What an image accepts

An image accepts a text, a sequence of scalar values, where the walk from state 0 over the whole of
it ends at a state that accepts. A walk reads a scalar value by finding the piece that holds it, and
then the span of the state it is at that holds that piece's class, and goes to the state the span
names. Every scalar value is in one piece and every class in one span of each state, so there is
one walk for each text, and the empty text is accepted where state 0 accepts.

## Readers and writers

An implementation may read P2 without writing it, or write it without reading it, as the README says
of the two entry points.

A writer writes an image of P2 that accepts what the pattern it was written from accepts. Which of
the deterministic machines that accept that it writes and how it numbers their states is the
writer's; how the classes are numbered is not, since the pieces decide it. Two writers may write
different images of one pattern, and neither is the right one: images are compared by what they
accept, never by their text.

A reader reads every image of P2 no longer than the most characters the README gives a writer, so
it reads whatever a writer of this repository's release writes. It may read longer ones too. An
implementation that reads P2 reads P1 as well, as the README asks of every format up to its release.

An image is one text. An implementation that has to carry it in parts, as Java cuts it into strings
of at most 65,535 characters so that each can be a constant of a class file, puts the parts back
together before it reads; how it cuts them is not part of the format.

## Fixtures

[`p2.txt`](p2.txt) holds images, some of P2 and some not, with what each accepts. Every
implementation that reads P2 runs it, as every implementation runs `suite/`. The lines are written
by hand from this file, not by a writer, and an image that is not one is there for each rule above.
`p2.txt` writes a line as `p1.txt` does.
